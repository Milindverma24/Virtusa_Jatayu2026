1 Overview

The problem

In an emergency, responders give drugs and perform procedures quickly and have no time to write them down. Notes end up on gloves, scraps of paper, or in memory. That causes three problems: the receiving hospital may not know a drug has already been given, doses and times written later from memory are often wrong, and nobody can later show exactly what happened and when.

What the system does

A responder speaks, types, or photographs a field note. Sanjeevani Lekh extracts every medication and procedure into a structured record, checks each value against the responder's own words, asks the responder to resolve anything uncertain, and then seals the confirmed record into an append-only log in which each record carries the hash of the one before it. From that log it prints a one-page handover for the receiving clinician.

Design principles

  • Never guess. A value must be traceable to words in the original note. If it is not, it is left empty and flagged, not filled in.
  • A human confirms every record. Items with a review flag must be accepted or removed before the record can be sealed.
  • Tamper-evident, not just stored. Records are hash-chained, and the database itself refuses updates and deletes.
  • Offline first, cloud optional. The whole flow works on the device. An optional online mode uses Groq, and any cloud failure falls back to the local models.
  • Always produce a draft. If the cloud and the local model are both unavailable, a built-in rule-based extractor still returns something the responder can review.

3 From note to record

3.1 Steps in detail

StepWhat happens
CaptureVoice goes to POST /draft/voice, typed text to /draft/text, a photo to /draft/image. Uploaded audio and images are deleted from disk after processing.
ExtractA model returns medications and procedures as JSON that must match a schema. The prompt (prompts/extract_v1.txt) requires that every item copy its exact words into source_text. Temperature is 0. One retry with a stricter prompt if the output does not validate.

4 Online and offline modes

4.1 How the mode is chosen

The field app has an ONLINE / OFFLINE switch in its top bar. It is sent with each request as the header X-Processing-Mode. Without the header the server default applies: PROCESSING_MODE=auto goes online when a Groq key is configured, and offline never contacts the cloud. Without a key the backend is always offline. In online mode any cloud failure (network, rate limit, invalid output after one retry) falls back to the local model, and then to the rule-based extractor. The engine that produced a draft is shown on the review screen and stored in the sealed record.

Privacy. In online mode the note text and recorded audio are sent to Groq, a third-party service. Use offline mode, or only synthetic data, wherever that is not acceptable. Photos are always read locally. Only the extraction and transcription steps use the cloud; validation, review and the audit log are always local.

5 Audit chain and data model

5.1 The audit_log table

ColumnMeaning
record_idUnique ID of the record, for example REC-CB7DCF11-01
encounter_idThe encounter the record belongs to; an encounter can hold several records
created_atTimestamp of sealing
input_typetext, voice or image
raw_textThe responder's words as captured
record_jsonThe confirmed FHIR-lite bundle
model_name, prompt_versionWhich engine and prompt produced the draft
reviewed_byResponder ID that confirmed the record
corrects_record_idSet when this record amends an earlier one; the earlier record is never edited
prev_hash, hashThe chain. The first record uses GENESIS
synced0 or 1. The only column that may change, and it is not part of the hash

5.2 Guarantees and their limits

  • hash is the SHA-256 of a canonical JSON (sorted keys) of all fields above plus prev_hash.
  • SQLite triggers abort any UPDATE to a content column and any DELETE, so the application cannot rewrite history even by mistake.
  • GET /audit/verify recomputes every hash in order and reports the first row that does not match.
  • Corrections are new records that point back to the one they amend.
What this does and does not prove. The chain makes tampering detectable. Someone with direct write access to the database file could rewrite the whole chain consistently, so the latest hash is only as trustworthy as the place it is kept. Printing it on the handover form is one way to anchor it outside the device.

5.3 Cloud sync and the dashboard

When a connection exists, POST /sync sends rows where synced = 0 to the Supabase audit_log table and then marks them synced. Rows are keyed by (device_id, record_id) and merged on conflict, so retrying never creates duplicates. The schema is in dashboard/supabase_schema.sql. The Next.js dashboard only reads: a shift board with one lane per vehicle, counts, a 14-day sparkline, an encounter table, an audit explorer and a quality page. Without Supabase credentials it shows built-in sample data and says so in its header.

7 User interface

The interface uses one identity across the landing page, the field app, the documentation and the dashboard: ECG-paper backgrounds, ink text, herb green for "verified" and amber for "needs a person". Dark monitor-style panels are used only where something is live. Type is Bricolage Grotesque for headings, IBM Plex Sans and Mono for text and data, and Tiro Devanagari for the wordmark संजीवनी लेख. The logo is a leaf (the Sanjeevani herb) with a heartbeat through it.

7.4 Handover report (PDF)

The handover is a plain one-page form: encounter, date, who confirmed it and how it was captured; medications and procedures in time order; the verbatim field note; the integrity line with the record ID and full hash; and a sign-off box for the receiving clinician. It contains no machine-written narrative, only what is in the confirmed record.

Requirements: Python 3, Node.js 20 or newer. For offline extraction, an Ollama server with the chosen model. Copy backend/.env.example to backend/.env and fill in the values you need.

11 Limitations and next steps

Limitations today

  • Not a medical device and not clinically validated. A responder must confirm every record.
  • The drug reference list has 17 drugs; anything else is flagged as unknown.
  • Online mode sends text and audio to a third party. Offline extraction needs Ollama, and without it the built-in rules are noticeably less accurate (section 4.2).
  • The on-screen live transcript uses the browser's speech recognition where available, and some browsers send that audio to the vendor. The saved record uses the backend's own transcription.
  • The audit chain detects tampering but does not by itself prove when records were created, because timestamps come from the device clock.
  • The dashboard is read-only and has no login of its own beyond the Supabase configuration.

Reasonable next steps (not built)

  • Measure the local Ollama model and Whisper on the same benchmark, and grow the benchmark beyond 20 notes.
  • Anchor the latest hash outside the device, for example on the handover form or in the cloud copy, and verify it on the dashboard.
  • Add automated browser tests for the review-and-confirm flow.
  • Broaden the drug reference and add configurable local protocols.
